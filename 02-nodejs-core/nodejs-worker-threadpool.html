Node.js — Thread Pool & Worker Threads

Phân tích cách Node.js xử lý tác vụ blocking với libuv Thread Pool và worker_threads module

Vấn đề cốt lõi: JavaScript single-threaded — nếu có tác vụ nặng (đọc file lớn, mã hóa, tính toán...) chạy trên Main Thread, toàn bộ server bị block. Node.js giải quyết bằng 2 cơ chế: libuv Thread Pool (tự động, cho I/O) và Worker Threads (thủ công, cho CPU-bound).

I/O-bound tasks → Thread Pool

Tác vụ chủ yếu chờ hệ thống (đọc file, query DB, DNS). CPU nhàn rỗi trong thời gian chờ.

  • fs.readFile, fs.writeFile
  • crypto.pbkdf2, crypto.scrypt
  • dns.lookup (không phải dns.resolve)
  • zlib compress/decompress
  • child_process.exec
Tự động — bạn chỉ cần gọi API, Node.js tự đẩy vào thread pool
CPU-bound tasks → Worker Threads

Tác vụ dùng nhiều CPU liên tục (tính toán, xử lý ảnh, parse JSON lớn). Sẽ block Main Thread nếu không tách ra.

  • Xử lý ảnh / video encoding
  • Machine learning inference
  • Parse JSON/CSV file lớn
  • Tính toán số học nặng
  • Cryptography tùy chỉnh
Thủ công — bạn tự tạo Worker, gửi data, nhận kết quả qua message
libuv Thread Pool là tập hợp các C-level threads chạy ngầm bên dưới Node.js. Mặc định 4 threads. Dùng để xử lý các tác vụ mà OS không cung cấp async API (không thể dùng epoll/kqueue).

Cấu hình & Giới hạn
  • Mặc định 4 threads — dùng tốt cho máy 4 cores
  • Tăng qua biến môi trường: UV_THREADPOOL_SIZE=16
  • Tối đa 1024 threads (khuyến nghị ≤ số CPU cores)
  • Nếu 4 threads đều bận → tác vụ mới vào hàng đợi, không bị drop
  • Network I/O (http, tcp) KHÔNG dùng thread pool — dùng OS async API
  • Nhiều thread pool task song song → chúng chia sẻ các thread, không phải chạy đồng thời tất cả
# Tăng thread pool size UV_THREADPOOL_SIZE=16 node app.js # Hoặc trong code (phải set TRƯỚC khi dùng) process.env.UV_THREADPOOL_SIZE = '16';

Worker Threads (module worker_threads) cho phép chạy JavaScript trong các thread riêng biệt. Mỗi worker có V8 instance và Event Loop riêng. Dùng cho CPU-intensive tasks mà thread pool không phù hợp.

Mỗi Worker: thread riêng, bộ nhớ riêng (không share heap), JS context riêng. Giao tiếp qua message passing (structured clone) hoặc SharedArrayBuffer (share raw memory).
main.js — Tạo và dùng Worker
const { Worker, isMainThread, workerData, parentPort } = require('worker_threads'); if (isMainThread) { // Chạy trên Main Thread const worker = new Worker(__filename, { workerData: { numbers: [1,2,3,4,5] } }); worker.on('message', (result) => { console.log('Result:', result); // 15 }); worker.on('error', console.error); worker.on('exit', (code) => { console.log(`Worker exited: \${code}\`); }); // Main thread KHÔNG bị block! console.log('Main thread free to work'); } else { // Chạy trên Worker Thread const { numbers } = workerData; const sum = numbers.reduce((a, b) => a + b, 0); parentPort.postMessage(sum); }
Worker Pool Pattern — tái sử dụng Worker
// worker-pool.js — Pool quản lý nhiều Worker class WorkerPool { constructor(workerFile, size = 4) { this.workers = []; this.queue = []; for (let i = 0; i < size; i++) { this._addWorker(workerFile); } } _addWorker(file) { const w = new Worker(file); w.busy = false; w.on('message', (result) => { w.busy = false; w._resolve(result); if (this.queue.length > 0) { const { data, resolve } = this.queue.shift(); this._run(w, data, resolve); } }); this.workers.push(w); } run(data) { return new Promise((resolve) => { const free = this.workers.find(w => !w.busy); if (free) this._run(free, data, resolve); else this.queue.push({ data, resolve }); }); } _run(worker, data, resolve) { worker.busy = true; worker._resolve = resolve; worker.postMessage(data); } }
SharedArrayBuffer — chia sẻ memory giữa threads
// Chia sẻ bộ nhớ thực sự (không cần serialize) const sharedBuffer = new SharedArrayBuffer(4); // 4 bytes const sharedArray = new Int32Array(sharedBuffer); // Main thread gửi buffer cho worker const worker = new Worker('./worker.js', { workerData: { sharedBuffer } }); // Đọc kết quả mà worker ghi vào (không cần postMessage) setTimeout(() => { console.log(sharedArray[0]); // Giá trị worker đã ghi }, 100); // Dùng Atomics để tránh race condition Atomics.store(sharedArray, 0, 42); const val = Atomics.load(sharedArray, 0);
Đặc điểm quan trọng của Worker Threads
  • V8 riêng: mỗi worker có heap riêng, GC riêng, không share JS objects
  • Event Loop riêng: worker có thể dùng setTimeout, Promise, fs... của riêng nó
  • Serialize khi gửi message: object được structured clone (deep copy) — overhead nếu data lớn
  • Transferable objects: ArrayBuffer có thể transfer (zero-copy) thay vì clone
  • require/import: Worker có thể dùng module bình thường
  • Không share globals: global, process.env được copy, không share reference
  • Thread cost: tạo Worker tốn ~5-10ms và vài MB RAM — nên dùng pool
  • isMainThread: để viết file chạy được cả ở main và worker

Khi nào dùng cái gì?
Tác vụ của bạn là gì? ├── Network request (HTTP, TCP, WebSocket) │ └── → Dùng bình thường (http, net...) — OS Async I/O tự xử lý ├── Đọc/ghi file, nén file (zlib) │ └── → Dùng fs, zlib bình thường — Thread Pool tự xử lý ├── Mã hóa mật khẩu (bcrypt, pbkdf2, scrypt) │ └── → Dùng crypto module — Thread Pool tự xử lý │ → Nếu cần nhiều concurrent: tăng UV_THREADPOOL_SIZE ├── Tính toán nặng (sort 10M records, image processing, ML) │ └── → Dùng Worker Threads │ → Tạo Worker Pool để tái sử dụng └── Cần chạy nhiều JS song song (microservices trong 1 process) └── → Worker Threads với MessageChannel

Tóm tắt xúc tích: V8 là engine C++ biên dịch và chạy JavaScript. Call Stack thuộc về V8, không phải libuv hay Node.js runtime. libuv điều phối khi nào chạy callback — V8 thực sự chạy nó trên Call Stack.
V8 Engine làm gì?
  • ① Biên dịch JS → Machine Code — dùng JIT (Just-In-Time): lần đầu compile nhanh, code chạy nhiều lần (hot code) được tối ưu lại sâu hơn. Không interpret từng dòng như ngày xưa.
  • ② Quản lý Heap (memory) — mọi object, array, closure bạn tạo đều nằm trong V8 Heap. V8 tự dọn rác qua Garbage Collector khi không còn reference nào trỏ tới.
  • ③ Duy trì Call Stack — theo dõi function nào đang chạy, function nào gọi function nào. Đây là Call Stack mà bạn thấy trong stack trace khi có lỗi.
  • V8 không biết gì về setTimeout, fs, http — đó là việc của libuv và Node.js bindings.
Call Stack thuộc về ai?

Call Stack là của V8 — không phải libuv, không phải Node.js runtime.

  • Khi libuv muốn chạy một callback (từ timer, I/O, Poll phase...), nó giao callback đó cho V8
  • V8 push callback lên Call Stack → thực thi → pop ra khi xong
  • libuv quyết định khi nào — V8 thực sự chạy
  • Đây là lý do "JavaScript single-threaded" — V8 chỉ có 1 Call Stack, chỉ chạy 1 thứ tại 1 thời điểm
