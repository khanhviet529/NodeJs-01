Nhóm 1 — Giao thẳng cho OS Kernel
Không dùng Thread Pool

Network I/O: HTTP, TCP, UDP, WebSocket... OS đã được thiết kế để xử lý hàng vạn kết nối mạng đồng thời từ thuở sơ khai của Internet.

  • Cơ chế: Card mạng nhận data → bắn ngắt phần cứng (hardware interrupt) → OS Kernel nhận và đưa vào hàng đợi — không cần thread nào phải "đứng chờ"
  • Trên Linux: epoll — đăng ký hàng nghìn socket, kernel tự báo khi có data
  • Trên macOS: kqueue
  • Trên Windows: IOCP (I/O Completion Ports)
  • libuv không dại tự làm — nó ném thẳng cho OS và Poll phase nhận callback khi kernel báo xong
APIs: http.get(), net.connect(), tcp socket, udp socket, WebSocket
Nhóm 2 — Ném vào Thread Pool
Dùng Thread Pool (mặc định 4 threads)

Hai loại tác vụ mà Node.js biết: để Main Thread tự làm sẽ bị đóng băng, còn nhờ OS làm kiểu non-blocking thì không tin tưởng được hoặc không khả thi.

Loại 2A — File System I/O (ổ cứng)
  • Lý do: Ổ cứng vật lý (đặc biệt HDD) phức tạp — file bị lock, phân mảnh, API async của OS không nhất quán giữa Windows/Linux/macOS
  • libuv giao cho thread phụ: "mày đứng im block ở đây chờ ổ cứng đọc xong, tao không tin OS làm việc này"
  • APIs: fs.readFile, fs.writeFile, fs.stat, fs.readdir...
Loại 2B — CPU-Intensive Tasks (tính toán nặng)
  • Lý do: Thuần túy là toán học, không liên quan I/O hay phần cứng — nhưng nếu Main Thread ngồi tính 2 giây thì server đóng băng 2 giây
  • Thread phụ âm thầm ngồi tính, Main Thread tiếp tục nhận request
  • APIs: crypto.pbkdf2, crypto.scrypt, zlib.gzip, dns.lookup
Kết quả: Thread Pool xong → libuv nhận → callback vào Poll Queue → Poll phase chạy callback trên Main Thread
